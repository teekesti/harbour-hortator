# The exercise edit dialog stages all fields locally and writes to the Exercise only on acceptance

`NameExerciseDialog` is widened from naming-only into a full Exercise edit dialog: name, work/rest type, duration, rounds, and reps (#10). It remains an *additional* path alongside the existing inline row controls in `FirstPage.qml`, which keep their current live-write behavior unchanged. The reps control is shown only while the staged type is "work" — hidden, not disabled, when staged as "rest" — matching the existing row's behavior of never surfacing reps for rest Exercises. The single context-menu entry that opened the naming-only dialog is renamed (e.g. "Edit exercise") rather than gaining a second, narrower entry alongside it.

All fields are staged locally in the dialog and written to the underlying `TimedExercise` only in `onAccepted`, never live as the user adjusts a control. The alternative was mirroring the row's live-`Binding` approach inside the dialog too. Picked deferred writes because a dialog implies Cancel/back discards changes — that only holds if nothing is written until acceptance — and because this already was the precedent set for the name field alone; extending it to the rest of the fields keeps one dialog-writing convention instead of two.

This surfaced an existing, unrelated gap: `ExerciseTimer::onExerciseChangedForTemplate` upserts a library template on every name/duration/reps change without checking `TimedExercise::isValid()`, so naming an Exercise and then driving its duration to zero (already possible via the row, with no new behavior from this dialog) silently persists a zero-duration template. Fixed by adding an `isValid()` guard there — a single engine-level fix that also covers the pre-existing inline-row path, not something duplicated in QML. Accepting the edit dialog itself is *not* gated on validity, matching the row's existing permissive behavior; only the template-library write is now guarded.
